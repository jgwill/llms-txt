# RISE Framework for LLMs
> A creative-oriented method in four phases, Reverse-engineer → Intent-extract → Specify → Export. It reads a prototype, names what its creator wanted to bring into being, writes that as prose code another LLM can build from, and lands the specification where it is built and remembered. A fifth movement, the Return, keeps the specification true as the code moves on. Each phase leaves a named file in `rispecs/`.

The RISE framework moves an LLM from reactive documentation to creative archaeology. It extracts and preserves the beloved qualities that make a prototype valuable, and it keeps the desired outcome in view while it does.

> **Phase numbers before 2.0.** Versions 1.x numbered Export as Phase 3 and maintenance as Phase 4, with Specify folded into Intent. So a citation of "RISE Phase 4" written before 2026-10-14 means [the Return](#the-return), and one of "Phase 3" from that time means [Export](#phase4-export).

## The Method at a Glance {#at-a-glance}

**R**everse-engineer → **I**ntent-extract → **S**pecify → **E**xport → ↺ Return

| Phase | The question it answers | What it leaves in `rispecs/<topic>/` |
|---|---|---|
| 1 · **R** Reverse-engineer | What does the prototype do, and what do people love in it? | `01-reverse-engineer.md` |
| 2 · **I** Intent-extract | What did its creator want to bring into being, and what is it in relationship with? | `02-intent.md`, and the kin file `<topic>.kin.md`: its relatives and what each relationship asks of us |
| 3 · **S** Specify | What is to be built, in prose another LLM can implement? | `SPEC.md` and `NN-<part>.spec.md`, or one `<topic>.spec.md` |
| 4 · **E** Export | Who takes it up, and where is it remembered? | `NN-export.md`, a row in `rispecs/README.md`, the `rispecs:` entry of the episode |
| ↺ Return | What has the code done since the spec was written? | `STATUS.md`, and the specs brought up to date |

Number prefixes keep the files in the order the phases wrote them. The full tree, the reserved names and how to move a misplaced spec are in **`llms-rispecs-layout.md`**.

R and I need not live in the same folder as S and E. When the reverse-engineering lives in an episode vessel or in the donor scripts, the topic's `README.md` says where, and the folder begins at its specs.

## SpecLang Foundation: Prose Code {#speclang-foundation}

RISE builds upon SpecLang's core insight: **specifications are "prose code"** - natural language representations of computation behavior that still require you to "think like a programmer."

### Key SpecLang Principles

**Spec as Source of Truth**
- The specification is what you maintain; executable code is secondary
- You rarely need to inspect generated code directly
- The spec captures *what you want* at the necessary level of detail

**Variable Detail Levels**
- Detail varies based on context and precision needs
- Offhand remarks may translate into dozens of boilerplate lines
- Exact protocol steps when precise behavior is critical
- The model infers idiomatic implementation from context

**"Create and Adjust"**
- Start simple, refine against running output
- Only detail the parts that need to change
- Stop when what you see matches what you want
- Use the model's ability to infer intent

**Bi-directional Ideation**
- The model "yes-ands" your intent, extending ideas naturally
- The model tells you where more precision is needed
- You are free of specifying common-sense requirements, and the creative process stays yours

**Intent-based Expression**
- Focus on behavior, let toolchain handle plumbing
- Setup, dependencies, and compilation are managed automatically
- Your attention stays on the spec, and the application that comes out runs in the real world

## Core Principles {#core-principles}

### Creative Orientation Over Reactive Approaches {#creative-orientation}
**Creative Orientation (RISE Approach)**
- Focuses on what applications enable users to create
- Oriented toward manifestation of desired outcomes
- Identifies structural dynamics that naturally advance progress
- Preserves creative consciousness embedded in code
- Creates specifications that support advancing patterns

**Reactive Approach (Traditional Pattern)**
- Focuses on issues that need elimination
- Oriented toward removing unwanted conditions
- Creates documentation that describes forced connections
- Generates oscillating patterns that move back-and-forth
- Results in specifications focused on reactive resolution

### Structural Tension Dynamics {#structural-tension}
**Structural Tension** is the dynamic relationship between:
- **Current Reality**: Present state of the system/user
- **Desired Outcome**: Specific results users want to create or desired state
- **Natural Resolution**: How tension moves the system toward the desired state

* NOT "Desired Structural State" just "Desired State".  Avoid adding words just to look like intelligent and make it greater than it is...

This represents natural tension dynamics rather than forced connections between states: the structural forces that move a system toward its desired outcome.

### Advancing vs Oscillating Patterns
**Advancing Patterns**: Structural relationships that support continuous movement toward desired outcomes
- Features that build upon each other systematically
- Natural progression through user journeys
- Structural dynamics that resolve tension forward

**Oscillating Patterns**: Structures that create back-and-forth movement without advancement
- Features that create dependency loops
- User interfaces that require repeated effort
- Systems that need constant maintenance to function

## The RISE Method {#rise-method}

**R**everse-engineer → **I**ntent-extract → **S**pecify → **E**xport

### Phase 1: Reverse-engineer (Creative Archaeology) {#phase1-reverse-engineering}

#### Purpose
Observe what the prototype does and what makes it valuable, before deciding anything about it. Phase 1 reads; it does not yet judge or design.

#### Discovery Process
**A. Core Creative Intent**
- What does this application empower users to create or achieve?
- What desired outcomes does it make possible?
- What structural tension exists between current user reality and desired results?

**B. User Creation Flows**
- Map all user journeys that lead to manifestation of desired outcomes
- Identify choice points where users advance toward their vision
- Note structural dynamics that naturally guide users toward goals

**C. Feature Inventory (Creation-Focused)**
- Vision-Supporting Features: Enable users to clarify desired outcomes
- Tension-Resolving Features: Carry natural progression toward goals
- Manifestation Features: Support actual creation of desired results

**D. Aspirational & Creative Goals**
- What desired states were the original creators working toward?
- What creative vision drove the design decisions?
- What structural patterns support advancing user progress?

**E. Structural Patterns Worth Preserving**
- Architectural decisions that enable natural progression
- Data flow patterns that support structural tension resolution
- Integration patterns that carry creative advancement
- Performance characteristics that keep creative flow

**F. Prototype Addresses**
When the input is a hosted prototype (for example a v0 app), record two addresses in the first specification written:
- **Published address**: where its behaviour is observed
- **Editing address**: where its chat and files are read

Later passes reach the same source through these two. An episode holding the prototype keeps the published address in its manifest and the editing address on the node, for the people who may edit.

#### What Phase 1 Leaves
`rispecs/<topic>/01-reverse-engineer.md`: the observations, sections A–F, with where each was seen (a file, a screen, a commit, a session). What the prototype stands on and what stands on it (packages, services, other repositories' contracts, its consumers) are observed here too, and become the first rows of the kin file. Evidence too large for one file (surveys, transcripts, deep-dive reviews) goes in `research/` beside it. When the observations live elsewhere (an episode vessel, the donor scripts), the topic's `README.md` names the place, and no `01-` file is written.

### Phase 2: Intent-extract {#phase2-intent-extract}

#### Purpose
Name what the prototype's creator wanted to bring into being, as distinct from what the code happens to do. Phase 2 turns the observations of Phase 1 into a desired outcome, a current reality, and the tension between them.

#### Intent Extraction Framework
For each component identified in Phase 1, extract:
- **Creative Intent**: What does this enable users to create or achieve?
- **Structural Intent**: How does this contribute to tension resolution?
- **Advancement Intent**: How does this support moving from current reality to desired outcome?

#### Desired Outcome Definition
- What specific result does the user want to create?
- How will they know when they've achieved this outcome?
- What makes this outcome valuable to them?

#### Structural Tension Analysis
- What is the current reality?
- What is the desired state?
- How does tension naturally progress toward the desired state?

#### Beloved Qualities
- What would users miss if it were gone?
- Which design decisions carry the creator's vision, and must survive a rewrite?

#### The Kin File: What the Spec Is in Relationship With
A specification is known through its relationships, and those relationships carry responsibility. *Relationship* here means relationality as Shawn Wilson writes it, not a database relation: see `llms-relationality.md`.

Phase 2 writes them down in the kin file. Each relative is named with how we are related, where it lives, and what the relationship asks of us. Five words say how we are related:
- **came from**: a person's words, an episode, a prototype, an earlier spec;
- **we rely on**: a package, a contract or a host kept elsewhere (upstream);
- **relies on us**: a package built from the spec, an app that uses it (downstream);
- **walks beside**: a neighbouring spec holding another part of the same work;
- **holds a decision**: a person or repository that decides something the spec touches.

The shape of the file, and how to write it, keep it true and read it before acting, are in **`llms-rispecs-kinship.md`**.

#### What Phase 2 Leaves
`rispecs/<topic>/02-intent.md`: the desired outcome, the current reality, the structural tension, and the beloved qualities. **The kin file** `<topic>.kin.md` is written now, with the folder's first spec, and every topic folder has one. A part with relationships of its own may have `NN-<part>.kin.md` beside its spec. A spec and its kin may also be written together as one `.rispec.md`.

### Phase 3: Specify {#phase3-specify}

#### Purpose
Write what is to be built as prose code: detailed enough that another LLM implements the surface from the specification alone, open enough that it infers the idiomatic rest.

#### What a Specification Holds
**1. Desired Outcome**: what the surface enables users to create, carried from Phase 2.

**2. Current Reality**: where things stand now, in plain facts. It takes no value word.

* Note that this is "**Current Reality**" NOT "Current Structural Reality" !!!

**3. Creative Advancement Scenarios**: the flows by which users reach the outcome, written in the format below instead of BDD scenarios.

**4. Supporting Structures**
- What application features enable this natural progression?
- How do these features support advancing rather than oscillating patterns?
- What structural relationships carry movement toward desired outcomes?

**5. Natural language describing the whole of the functional aspects**: screens, components, data, behavior, in SpecLang syntax.

#### Creative Advancement Scenario Format {#creative-advancement-scenarios}
```
**Creative Advancement Scenario**: [Scenario Name]

**User Intent**: [Desired outcome they want to create]
**Current Reality**: [Starting state/context]
**Natural Progression Steps**:
  1. [Structural dynamic enables...]
  2. [System responds by...]
  3. [User advances toward...]
**Achieved Outcome**: [Manifested desired result]
**Supporting Features**: [Application capabilities enabling this advancement]
```

#### SpecLang Specification Syntax {#speclang-syntax}

RISE specifications follow SpecLang's structured Markdown format. This provides consistent organization while maintaining natural language expressiveness.

```markdown
# ApplicationName
Brief description of what the application enables users to create.

## Screens
### ScreenName
Description of what users accomplish on this screen.
- **Behavior:** What happens, how data flows
- **Layout:** Contains `ComponentA` and `ComponentB`

## Components
### ComponentName
Description of the component's purpose.
- **Behavior:** User interactions and responses
- **Styling:** Visual presentation details
- **Layout:** Child component arrangement (if applicable)

## Data
### ModelName
Description of data structure and relationships.
```

| Element | Purpose | Example |
|---------|---------|---------|
| `# Title` | Application/spec name | `# SpecNews` |
| `## Section` | Major groupings | `## Screens`, `## Components`, `## Data` |
| `### Name` | Individual screens/components | `### Home Page`, `### Header` |
| `**Behavior:**` | Actions, interactions, data flow | `On tap, triggers the \`PostList\` to refresh` |
| `**Styling:**` | Visual presentation | `Fixed at top, large font, background color` |
| `**Layout:**` | Component composition | `Contains a \`Header\` and a \`PostList\`` |
| \`BacktickRef\` | Cross-component references | `Renders a list of \`PostItem\` components` |

#### Structural Tension in Spec Elements

The `**Behavior:**`, `**Styling:**`, and `**Layout:**` sections map directly to structural tension dynamics:

- **Behavior** defines the *underlying structure* that determines how the application functions: the primary driver of structural tension resolution. When reverse-engineering, behavior reveals the structural dynamics that enable users to advance toward desired outcomes.

- **Styling** and **Layout** represent the *manifestation layer*. They must be explicitly reverse-engineered because they encode design decisions that support (or hinder) the user's natural progression through the application.

The hierarchy (`## Screens` → `## Components` → `### ComponentName`) mirrors how structural tension flows through an application: from high-level user outcomes (screens) to the building blocks (components) that enable those outcomes.

#### Detail Level Examples

**Minimal (context-inferred)**:
```markdown
- At the bottom show two buttons "Cancel" and "Submit"
```

**Detailed (precise behavior)**:
```markdown
- Continuously poll the server on progress on the route `/progress?taskId=$id`
- The server responds with a JSON object with the following fields:
  - progress: number
  - output: string
  - errors: string
- When progress reaches 100%, redirect to `/success?taskId=$id`
```

#### Specification Autonomy and Implementation Agnosticism

RISE specifications are **autonomous from any specific codebase**. They describe the system's desired behavior, structural dynamics, and creative intent independently of its implementation language, framework, or existing code.

*   **Codebase-Agnostic**: A RISE specification is complete enough for another LLM (or human developer) to **re-implement the entire system from scratch**, without access to the original source code.
*   **Conceptual References**: References within a RISE specification (e.g., to "Prompts Specification," "Data Schemas," or "API Definitions") are **pointers to other RISE specifications**, not file paths within an existing codebase. Within a `rispecs/` folder, those other specifications sit beside it: `./03-data-models.spec.md`.
*   **"Black Box" Principle**: The specification describes the system as a "black box" from an implementation perspective. It says *what* the system does and *how* it reaches desired outcomes through structural dynamics, not *how* it is currently coded.

#### Drawn Specifications {#drawn-specifications}

Behaviour, data and usage can be drawn instead of written:

| What it describes | Drawing | File |
|-------------------|---------|------|
| Behaviour | state machine | `*.smdf.json` |
| Data | entity-relationship drawing | `*.erdf.json` (Spec 80) |
| A usage scenario | sequence drawing | `*.sqdf.json` (Spec 81) |

One `*.sysdf.json` (Spec 82) lists which drawings belong together. A sequence drawing is the drawn form of a Creative Advancement Scenario. Write the prose scenario first and draw it when messages between actors matter. A drawing sits beside the spec that cites it.

#### Quality Criteria
- ✅ Creating Focus: Emphasizes what users create, not problems solved
- ✅ Structural Dynamics: Natural forces driving progression (the disequilibrium between current reality and what is desired)
- ✅ Advancing Patterns: Movement toward outcomes
- ✅ Desired Outcomes: Clear, specific results users want
- ✅ Natural Progression: Movement through structural dynamics, not forced effort

#### Anti-Patterns to Avoid
- ❌ Forced connection thinking: "Bridging the gap between X and Y"
- ❌ Reactive approach bias: "This eliminates the issue of..."
- ❌ Force-based language: "Users must..." or "Requires determination"
- ❌ Oscillating patterns: Back-and-forth movement descriptions
- ❌ BDD scenarios: Traditional reactive scenario structures

#### What Phase 3 Leaves
The specification files of the topic folder:
- `SPEC.md`: the master, the whole surface and how its parts compose, when the surface is specified in parts. In a numbered family, `00-<topic>-master.spec.md` holds this role.
- `NN-<part>.spec.md`: each part, numbered in reading order after `01-reverse-engineer.md` and `02-intent.md` when those exist.
- `<topic>.spec.md`: the whole surface, when one file holds it.

Evaluate the work by asking: if another LLM took what was written, would it implement the functionality adequately?

### Phase 4: Export {#phase4-export}

#### Purpose
The specification leaves its author. It lands where its readers will find it, it is written for each reader who takes it up, and it is recorded where the work is remembered. Implementation follows Export: an implementer, a harness or a code generator builds from what Phase 4 hands over. That building is not a fifth letter of RISE, and the Return keeps it and the specification in step.

#### Where Specifications Land {#where-specifications-land}

Specifications land in the `rispecs/` folder at the root of the repository or package they describe, one folder per surface (for example `./rispecs/llm_prompt_support/`, with `llm_prompt_support.spec.md` describing how the LLM supports an app). The full tree, the reserved names, the reading order, and how to move a spec that sits in the wrong place are in **`llms-rispecs-layout.md`**. In short:

```
rispecs/
├── README.md                    roadmap: one row per topic folder, with status
├── AGENTS.md                    optional: this repository's overrides of this list
└── <topic>/                     one folder per surface, kebab-case
    ├── README.md                the topic's roadmap: outcome, files in reading order, status
    ├── 01-reverse-engineer.md   1 R  what the prototype does, observed
    ├── 02-intent.md             2 I  desired outcome, current reality, tension
    ├── SPEC.md                  3 S  master: the whole surface, and how its parts compose
    ├── 03-<part>.spec.md        3 S  a part: what to build
    ├── <topic>.kin.md           2 I  the kin file: its relatives, and what each relationship asks of us
    ├── 03-<part>.kin.md         2 I  a part's own relatives, when it has some
    ├── 04-<part>.rispec.md      3 S  a part and its kin in one file
    ├── 05-export.md             4 E  how an implementer, a harness or an episode takes it up
    └── STATUS.md                ↺    what is built, what is not yet
```

- **Which folder**: ask "whose part is this?" A `rispecs/` that describes several surfaces holds only `README.md` and `AGENTS.md` at its root, and one folder per surface. A `rispecs/` that describes one surface (a package, a single app) is that surface's folder, and its parts sit at its root.
- **Which order**: the two-digit prefix is reading order, and reading order follows R → I → S → E.
- **Moving**: moving a spec changes its folder, never its file name. Code comments, AGENTS files and episode manifests cite specs by name.

`_archived_*.md` files are frozen: do not edit them and do not implement from them. A repository's own `rispecs/AGENTS.md` overrides this list.

#### Writing for Each Reader

The same specification is taken up by different readers. An export file (`NN-export.md`) writes for the one who builds next; the others are reached through the README and, when asked for, a document of their own.

**1. Development Team Export** (the usual `NN-export.md`)
- Creative Advancement Scenarios: Detailed outcome-creation flows
- API Specifications: Endpoints enabling desired outcome achievement
- Data Models: The structure of the relationships that supports advancement
- Testing Frameworks: Validating creative advancement patterns
- For a harness or plugin: the recipe per harness, and the gates that prove it built

**2. Technical Documentation Export**
- Architecture Overview: How structural dynamics enable desired outcomes
- Feature Specifications: What each feature enables users to create
- Technical Requirements: Supporting infrastructure for advancing patterns
- Implementation Guidelines: Preserving creative orientation in code

**3. Stakeholder Communication Export**
- Value Proposition: What users can create through this system
- Success Metrics: Measuring advancement toward desired outcomes
- Resource Requirements: Supporting structural dynamics implementation
- Timeline Planning: Natural progression phases

**4. User Experience Export**
- User Journey Maps: Advancing patterns through desired outcome creation
- Interface Requirements: Supporting natural progression
- Interaction Principles: Enabling rather than forcing user advancement
- Usability Guidelines: Adequate dynamics in interface design

#### Recording the Export {#recording-the-export}

The export is complete when the episode that prompted it lists its products in `episode.yaml`:
- `rispecs:` the spec folders, with `derived_from` naming the prototype and `system` naming the stateloom system drawing. Each entry is cited as `rise://<owner>/<repo>/rispecs/<topic>/<entry file>`, pinned to the commit the episode stood on.
- the drawings
- `prototypes:` each prototype with its published address (the editing address stays on the node)

The Return starts from these lists.

#### What Phase 4 Leaves
- `NN-export.md` in the topic folder, numbered after the specs: what the next builder needs, and how they prove it built.
- A row for the topic in `rispecs/README.md`: its desired outcome in a sentence, its status, its issue.
- **Named from both sides.** Each relative that relies on the spec (a package, an app, a plugin) names it back in its own kin file or `KINSHIP.md`, or receives an issue asking it to.
- The `rispecs:` entry in the episode's `episode.yaml`.

### ↺ The Return: Keeping Specifications Alive {#the-return}

#### Purpose
A specification is true on the day it is exported. The Return keeps it true as the code moves on: it is a RISE pass run on what changed. R reads the git history since the specification, I reads the intent in the commit messages, S writes the change into the specs, and E records the new state in `STATUS.md` and in the episode.

**Current reality**: commits land daily and specification updates are manual and infrequent. **Desired outcome**: specifications that match the code at each release. The Return holds that tension with a staleness timeline and an upgrade workflow driven by git history.

#### Step 1: Staleness Timeline (R)

Date the specification against the code. In a fresh clone every file time is the checkout time, so ask git rather than `ls`:

```bash
# Last commit that touched the topic's specs
git log -1 --format='%cs %h %s' -- rispecs/<topic>/

# Commits to the code since then
LAST_SPEC_DATE="2025-12-15"
git log --since="$LAST_SPEC_DATE" --pretty=format:"%h - %s (%ar)" --no-merges

# Example Output:
# cc73aec - Responsive Implementation (2 days ago)
# a247fd8 - Restored Gemini, was not leading anymore (2 days ago)
# 4859929 - SDK removal (2 days ago)
```

On a long-lived checkout, `ls -ltra ./rispecs/<topic>/` gives the same reading. A `rispecs/` that describes one surface (a single app, as in the case study below) is listed at its root.

**What This Reveals**:
- **Elapsed Time**: How many days/hours between last spec edit and latest commit
- **Commit Count**: Number of changes the specs do not yet carry (e.g., 12 commits in the 2 days since the last spec)
- **Distance**: The longer the elapsed time, the further the code has moved from what the specs describe

#### Step 2: Commit Message Mining (I)

Use commit messages as breadcrumbs to what changed and why.

```bash
git log --since="$LAST_SPEC_DATE" --pretty=format:"%h|%s|%an|%ar" --no-merges

# Example Output:
# cc73aec|Responsive Implementation|Mia|2 days ago
# a247fd8|Restored Gemini, was not leading anymore|Mia|2 days ago
# 4859929|SDK removal|Mia|2 days ago
```

1. **Feature Additions**: Keywords like "Add", "Implement", "Create"
   - Example: "Add keyboard navigation system" → Update `ui.spec.md`
2. **Refactors**: Keywords like "Refactor", "Restructure", "Migrate"
   - Example: "Refactor Gemini SDK → REST API" → Update `tools.spec.md` + `mcp-bridges.spec.md`
3. **Fixes with Architectural Weight**: Keywords like "Fix", "Resolve" + technical detail
   - Example: "Fix White Screen (SDK removal)" → Documents a design decision
4. **Developer Intent**: Well-written commits encode "why"
   - Example: "Restored Gemini, was not leading anymore" → Implies SDK failed, REST succeeded

Disciplined commit messages give every change its why. Thin ones send you back to reading the code.

#### Step 3: Differential Analysis (I → S)

Map changed files to the specs that describe them.

```bash
git diff --name-only $LAST_SPEC_DATE..HEAD
git diff $LAST_SPEC_DATE..HEAD -- src/App.tsx
```

| Changed File(s) | Rispec File to Update | Reason |
|----------------|----------------------|--------|
| `src/App.tsx` | `ui.spec.md` | Main component orchestration changes |
| `services/latticeWeaver.ts` | `tools.spec.md` + `mcp-bridges.spec.md` | New Gemini service layer |
| `components/*.tsx` | `ui.spec.md` | New UI components (ShortcutHelp, ResonanceMeter) |
| `public/manifest.json` | `data-models.spec.md` | PWA schema addition |
| `types.ts` | `data-models.spec.md` | Type definition changes |

When the specs live in another repository than the code, run the git log in the code's repository and date the specs in theirs.

#### Step 4: Specification Update (S)

For each affected spec:

1. **Read Implementation**: Use git diff output + file reads to understand exact changes
2. **Extract Creative Intent**: What does this enable users to create?
3. **Write with RISE Principles**:
   - Focus on desired outcomes (not problems solved)
   - Use structural tension framing (current reality → desired state)
   - Include implementation-sufficient detail (another LLM can code from spec)
   - Keep advancing pattern language (natural progression, not forced effort)

A spec part that grows a family of its own becomes a sub-topic folder (`llms-rispecs-layout.md`). A new part takes the next free number. Numbers already given are never reused.

**Example (from Narrative Lattice Weaver upgrade)**:

```markdown
## Part 8H: Responsive Canvas with ResizeObserver (Iteration 14-15)

**Creative Intent**: Users create lattice explorations on any device—mobile, tablet, desktop—without fixed-size limitations.

**Responsive Implementation**:

\`\`\`typescript
const containerRef = useRef<HTMLDivElement>(null);
const [dimensions, setDimensions] = useState({ width: 0, height: 0 });

useEffect(() => {
  const updateDimensions = () => {
    if (containerRef.current) {
      const { width, height } = containerRef.current.getBoundingClientRect();
      setDimensions({ width, height });
    }
  };

  const resizeObserver = new ResizeObserver(() => {
    updateDimensions();
  });

  if (containerRef.current) {
    resizeObserver.observe(containerRef.current);
  }

  return () => resizeObserver.disconnect();
}, []);
\`\`\`

**What This Enables**:
- **Mobile Lattices**: Visualizer works on phones without horizontal scroll
- **Sidebar Tolerance**: When universe cards collapse, canvas reflows gracefully
- **Projection Mode**: Fullscreen presentation adjusts to any screen aspect ratio

**Implementation Reference**: Commit cc73aec "Responsive Implementation"
```

- ✅ Creative orientation: "Users create lattice explorations"
- ✅ Code snippets: Implementation-sufficient TypeScript
- ✅ "What This Enables" section: Outcome-focused bullets
- ✅ Git traceability: Commit reference establishes provenance

#### Step 5: Validation and Record (E)

✅ **All Commits Since the Last Spec Analyzed**
- Every commit from the period since the last spec reviewed
- Commit messages cross-referenced with rispec updates
- No commit left without a place in the specs, or a stated reason it has none

✅ **New Features Written with Desired Outcomes**
- Each feature framed as "what users create"
- No reactive language ("this fixes", "this eliminates")
- Structural tension established (current reality → desired state)

✅ **Creative Orientation Preserved**
- Language patterns: "enables", "creates", "natural progression"
- Avoided patterns: "bridges gap", "solves problem", "forces user to"

✅ **Implementation-Sufficient Detail**
- Another LLM can implement from specs alone
- Code snippets included where architectural patterns matter
- Types/schemas provided for data structures
- API contracts specified (endpoints, parameters, returns)

✅ **Cross-Reference Coherence**
- Updated rispec files reference each other correctly
- Data model changes reflected in tool specifications
- UI component specs align with architectural diagrams

✅ **Relationships Checked**
- Every relative in the kin file checked: a moved path, a newer version, a new relative, a changed contract
- What was out of balance fixed where the relationship lives, not only here (`llms-rispecs-kinship.md` § When a relationship is out of balance)
- A dated Harmony entry in the kin file

✅ **Git Provenance and Record**
- Commit hashes cited for major features ("Implementation Reference")
- `STATUS.md` says what is built and what is not yet, as of which commit
- The episode that asked for the Return lists the specs it touched

**"Black Box" Test**: Can another LLM re-implement the complete system from the upgraded specs without accessing source code?

#### Return Anti-Patterns

❌ **Batch Updates Without Git Analysis**
- **Wrong**: "I'll just read all the code and update specs manually"
- **Right**: Start with git log to understand timeline and intent

❌ **Reactive Framing**
- **Wrong**: "Added export feature to fix users not being able to save sessions"
- **Right**: "Users create portable lattice artifacts—downloadable JSON preserving complete session state"

❌ **Implementation Details Without Creative Intent**
- **Wrong**: "Added ResizeObserver to LatticeVisualizer.tsx"
- **Right**: "Creative Intent: Users create lattice explorations on any device... [then implementation]"

❌ **Missing Git Provenance**
- **Wrong**: "Gemini integration now uses REST API"
- **Right**: "Gemini REST API Integration (Commit a247fd8: 'Restored Gemini')"

❌ **Spec-Code Timestamp Inversion**
- **Wrong**: Updating rispecs months after implementation
- **Right**: Regular Returns (weekly or per sprint) to keep the distance between code and spec short

#### Case Study: Narrative Lattice Weaver (Dec 2025)

- **Baseline**: 10 rispec files (4,686 lines) at the root of a one-app `rispecs/`, last modified Dec 15 05:05 UTC
- **Implementation**: UI prototype evolved Dec 13-15 (Iterations 10-15, 12 commits)
- **Distance**: 2 days, 10+ features the specs did not yet carry

**R — Staleness timeline**: `git log --since="2025-12-13" --oneline --no-merges` → 12 commits (cc73aec Responsive Implementation, a247fd8 Restored Gemini, 4859929 SDK removal, …).

**I — Commit mining**: Iteration 10: localStorage persistence, keyboard nav, playback, ResonanceMeter · Iteration 11: in-context editing, session export, resonant arcs · Iteration 12: Gemini AI weaving (SDK → REST API) · Iteration 13: PWA manifest, icon.svg · Iterations 14-15: ResizeObserver responsive canvas.

**I → S — Differential analysis**:
```bash
$ git diff --name-only 2025-12-13..HEAD
src/App.tsx                       # → ui.spec.md (persistence, keyboard, export)
services/latticeWeaver.ts         # → tools.spec.md (new tool: lattice_weave_generative)
components/LatticeVisualizer.tsx  # → ui.spec.md (ResizeObserver responsive)
components/ShortcutHelp.tsx       # → ui.spec.md (new component)
components/ResonanceMeter.tsx     # → ui.spec.md (new component)
public/manifest.json              # → data-models.spec.md (PWA schema)
```

**S — Update**: `ui.spec.md` 704→1,145 lines (8 new sections for 7 UI features) · `tools.spec.md` 452→639 lines (Category 8: Generative Weaving tool) · `data-models.spec.md` 290→462 lines (4 new schemas). Total +800 lines carrying every change the specs had not yet described.

**E — Validation**: all 12 commits mapped to rispec sections; every feature has a "What This Enables" section; commits cc73aec, a247fd8, 4859929 cited; another LLM can implement the Gemini integration from `tools.spec.md` alone.

**Lessons**:
- **Commit Discipline = Upgrade Velocity**: "Restored Gemini, was not leading anymore" carried the architectural context in one line
- **Two Days of Distance Stays Small**: Short Returns keep each one short
- **Git Log as Archaeological Tool**: Timeline reconstruction took minutes, not hours

#### Tools for the Return

**Today**: `git log` and `git diff` by hand, the RISE quality checklist, and `rispecs_layout_check.py` (jgwill/llms-txt) for the shape of the folder.

**Possible tools**:
1. **Staleness report**: a CI check that names the topics whose last spec commit is older than the code they describe by more than 7 days
2. **Commit-to-Rispec Mapper**: an agent that reads commit messages and proposes which specs a Return should touch
3. **Draft Return sections**: an LLM drafts rispec sections from git diffs for human review

**MCP Tool Shapes**:

- `rise_suggest_upgrades(commit_hash)` → proposed rispec edits for a commit

## Implementation Guidelines for LLMs

### Iterative Refinement Workflow ("Create and Adjust")

Iterative specification development through the MMOT planning → executing → learning loop (see `llms-managerial-moment-of-truth.md`).

**1. Start Minimal** (Planning)
- Begin with high-level desired outcome description
- Let structural tension guide what needs specification
- Trust context inference for common patterns

**2. Observe Current Reality** (Executing + Acknowledging Truth)
- Generate/compile specification
- Observe what emerges
- Identify tension between vision and reality
- This is the "Moment of Truth" - either lead (refine) or overlook

**3. Refine Selectively** (Analyze + Action Plan)
- Only add detail where the output diverges from intent
- Analyze *how* the divergence occurred (structural dynamics)
- Preserve successful inferences (don't over-specify)
- Each refinement should resolve specific desires.

**4. Stop When Aligned** (Learning Complete)
- What you see matches what you want
- Specification captures intent at necessary detail level
- Further specification would create unnecessary rigidity
- Record the achieved state in `STATUS.md`

**Connection to MMOT**: Each iteration is a "moment of truth" where you acknowledge tension between desired outcome and current reality, analyze the dynamics that produced the current state, and refine to advance toward alignment.

**Anti-pattern**: Exhaustive up-front specification before any feedback loop (reactive "fix everything first" orientation).

### Language Patterns for Creative Orientation {#language-patterns}

**Use These Patterns**:
- "What does this enable users to create?"
- "Desired outcomes" vs. "reactive elimination"
- "Structural dynamics" vs. "forced connections (or free-association)"
- "Natural progression" vs. "imposed advancement"
- "Structural tension progression" vs. "artificial linking"
- "Advancing patterns" vs. "improvement cycles"
- "Creative advancement" vs. "user journey optimization"

**Avoid These Patterns**:
- "This eliminates the issue of..."
- "Connecting disparate elements..."
- "Users need to navigate..."
- "Correcting deficiencies with..."
- "Handling complications of..."

See `llms-language-integrity.md` for the word-level patterns: decorative adjectives, false-work verbs, hedging.

### Structural Analysis Framework

When analyzing code through RISE:

1. **Identify Creative Enablers**: What does each component allow users to create? (Phase 1)
2. **Map Tension Dynamics**: How does the system naturally progress toward desired outcomes? (Phase 2)
3. **Preserve Beloved Qualities**: What makes users love this functionality? (Phase 2)
4. **Specify Advancement Patterns**: How do features support progression toward the outcome? (Phase 3)
5. **Redesign Oscillating Elements**: Name the back-and-forth patterns, and specify the advancing structure that replaces them (Phase 3)

### Quality Assurance Checklist

For each RISE analysis, validate:

**✅ Creative Orientation Preserved**
- Focuses on what users create through natural progression
- Emphasizes desired outcomes over reactive elimination
- Uses advancing pattern language throughout
- Describes structural dynamics through organic connections

**✅ Structural Dynamics Maintained**
- Natural progression rather than forced advancement
- Tension progression toward desired states
- Movement carried by structural relationships
- No dependency on willpower or determination

**✅ Technical Accuracy**
- Implementation details support creative orientation
- Architecture enables advancing patterns
- Code guidelines preserve structural dynamics
- Testing validates outcome creation through natural progression

**✅ Landed and Recorded**
- Each file sits in the folder of its surface, named for its phase (`llms-rispecs-layout.md`)
- The topic has a row in `rispecs/README.md`
- The episode that asked for the work lists the spec folder
- The folder has a kin file, and its relationships are named from both sides

- Test creative advancement scenarios instead of edge cases

- Focus on what endpoints enable users to create

- Design data flows that support natural progression
- Write creative advancement patterns for developers into the export

### System Architecture
- Organize components around creative enablement

- Create patterns that advance rather than oscillate
- Build infrastructure for natural user progression
- One `rispecs/` topic folder per surface the architecture names

## Integration with Creative Orientation

### Fundamental Creative Principles

**1. Choice Hierarchy**
- Fundamental choices: States of being or general life orientation
- Primary choices: Specific results you want to create
- Secondary choices: Actions taken to support primary choices

**2. Three-Phase Creative Process**
- **Germination**: Initial excitement and vision formation
- **Assimilation**: Building momentum and developing structure
- **Completion**: Finishing touches and manifestation

**3. Structural Tension as Creative Force**
- Natural dynamic system seeking equilibrium through organic progression
- Creates natural movement toward desired outcomes
- Functions independent of willpower or determination
- Requires clear vision of both current reality and desired results

### Creative vs Reactive Mindset

**Creative Mindset (RISE Aligned)**:
- Focuses on what you want to create
- Operates from vision
- Creates structural dynamics from current reality to desired outcomes
- Builds advancing patterns toward desired outcomes

**Reactive Mindset (Avoid)**:
- Focuses on what you want to eliminate
- Operates reactively to circumstances
- Creates temporary fixes that oscillate
- Builds around removing unwanted conditions

## Common Pitfalls and Corrections

### Pitfall 1: Forced Connection Thinking
**Incorrect**: "This feature bridges the gap between user needs and system capabilities"
**Correct**: "This feature enables users to create desired outcomes through natural structural progression"

### Pitfall 2: Reactive Focus
**Incorrect**: "This API eliminates data access complications"
**Correct**: "This API enables users to create data relationships that advance toward their desired information outcomes"

### Pitfall 3: Force-Based Language
**Incorrect**: "Users must complete these steps to achieve their goals"
**Correct**: "Users naturally progress through these steps as structural dynamics advance toward their desired outcomes"

### Pitfall 4: Oscillating Pattern Design
**Incorrect**: "Users can toggle between different views to find what they need"
**Correct**: "The interface advances users toward their desired information through progressive disclosure that builds understanding"

### Pitfall 5: Specs Without a Place
**Incorrect**: A new `feature.spec.md` dropped at the `rispecs/` root beside twenty topic folders, or two layouts offered as equal options
**Correct**: Ask "whose part is this?", write the file into that surface's folder, and give it its phase's name (`llms-rispecs-layout.md`)
