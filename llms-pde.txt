# Prompt Decomposition Engine (PDE) — llms-txt Reference

> Intention exploration as EAST practice: decomposing prompts into explicit and implicit intents, mapping dependencies through Four Directions, and holding ambiguities as productive tension.

**Version**: 0.3
**Document ID**: llms-pde-v0.3
**Last Updated**: 2026-05-31
**Content Source**: Derived from practical PDE usage, the medicine-wheel-prompt-decomposition npm package, the current `miaco decompose run --help` surface, and implementation in miaco (lean CLI) and mcp-pde / miadi-code (MCP lineage).

---

## Purpose

PDE transforms a complex prompt into a structured decomposition that:

1. Identifies **primary** and **secondary** intents (explicit and implicit)
2. Maps each intent to a **Four Directions** position (East/South/West/North)
3. Surfaces **ambiguities** as named tensions — not silently resolved assumptions
4. Produces an **action stack** respecting dependencies between tasks

---

## Four Directions in PDE

The standard PDE directions (adapted from creative-orientation practice):

| Direction | Role in Decomposition | Phase |
|-----------|----------------------|-------|
| 🌅 **East** — Vision | Understanding what is being asked; clarifying requirements; envisioning desired outcomes | Germination |
| 🔥 **South** — Analysis | Research, learning, investigation, growth tasks; planning with human and AI companions | Assimilation |
| 🌊 **West** — Validation | Testing, reflection, review, accountability checks | Assimilation |
| ❄️ **North** — Action | Implementation, execution, delivery, completion | Completion |

**Note**: These directions are a starting point. The creative-orientation llms-txt suggests they may be adjusted as practice evolves. PDE is itself an EAST practice — the decomposition is part of the visioning phase where intentions are explored before action begins.

## Decomposition Structure

```json
{
  "primary": {
    "action": "main action verb",
    "target": "what the action applies to",
    "urgency": "immediate|session|persistent",
    "confidence": 0.0-1.0
  },
  "secondary": [
    {
      "action": "verb",
      "target": "target",
      "implicit": true/false,
      "dependency": "what this depends on",
      "confidence": 0.0-1.0
    }
  ],
  "directions": {
    "east": [{"text": "vision items", "confidence": 0.0-1.0, "implicit": false}],
    "south": [{"text": "analysis items"}],
    "west": [{"text": "validation items"}],
    "north": [{"text": "action items"}]
  },
  "actionStack": [
    {"text": "task", "direction": "east|south|west|north", "dependency": "or null"}
  ],
  "ambiguities": [
    {"text": "ambiguous part", "suggestion": "how to clarify"}
  ]
}
```

---

## Key Principles

### Implicit Intent Extraction

PDE extracts implicit intents from hedging language: "I assume," "probably," "somehow," "you will need," "I expect." These are flagged with `"implicit": true` and lower confidence scores.

### Delayed Resolution of Ambiguities

Ambiguities are **named and surfaced**, not silently resolved. This honors the delayed-resolution principle — holding productive tension rather than collapsing it through premature assumptions.

### Confidence Scoring

Each intent carries a confidence score (0.0–1.0) reflecting how clearly it was stated. Explicit requests score high; implicit inferences score lower. This transparency enables the human steward to adjust course.

---

## PDE as Relational Practice

When used with an AI companion, PDE is a **ceremonial act of shared visioning**:

- The human brings the intention (however messy or complex)
- The AI companion surfaces what was said and what was implied
- Together they refine the vision before entering SOUTH (planning) and NORTH (action)
- Ambiguities become conversation starters, not blockers

## Storage

Decompositions are stored in `.pde/` as paired JSON and Markdown files within timestamped folders:

```
.pde/
  <YYMMDDHHmm>--<uuid>/
    pde-<uuid>.json   — machine-readable structured decomposition
    pde-<uuid>.md     — human-editable Four Directions document
```

- Legacy format: `.pde/<uuid>.json` + `.pde/<uuid>.md` (flat, without folder)
- The markdown file is designed for human annotation — the steward can edit, add notes, correct interpretations, and refine the vision before work begins
- Parent-child nesting: a decomposition can reference a `parent_pde_id`, and child folders are stored inside the parent's folder

### Companion Artifacts

Additional files may appear alongside the PDE pair:

- `pde-inquiry-enrichment.md` — knowledge base search results (from `qmd search`/`qmd query`) that enrich the decomposition with discovered content
- `pde-four-questions.md` — Structural Thinking Four Questions generated from the decomposition's ambiguities and intents (see `llms-pde-structural-thinking.md`)

## PDE → Structural Thinking Bridge

PDE surfaces ambiguities at EAST. The Four Questions (`llms-st-four-questions.md`) transform those ambiguities into structured inquiry at SOUTH:

| PDE Output | Question Type | What It Produces |
|------------|--------------|------------------|
| Vague intents (low confidence) | **Information** | Specific details that make the picture concrete |
| Terms used without definition | **Clarification** | The speaker's specific meaning |
| Hedging language ("I assume", "probably") | **Implication** | What is implied but not stated — verified with the speaker |
| Contradictory intents or assumptions | **Discrepancy** | Where underlying structure may need to change |

This bridge is implemented in `miaco pde-to-st run --pde <uuid>` and documented in `llms-pde-structural-thinking.md`.

## Implementation Architectures

Two lineages implement PDE with different trade-offs:

### Lean Lineage (miaco)

Single-file implementation (`decompose.ts`) with multi-engine dispatch, strategy selection, parent-child PDE nesting, engine fallback, and `.pde/` persistence. For current agent work, **prefer `miaco decompose run`** as the operational entrypoint because it exposes the newest strategy and provenance controls.

```bash
miaco decompose run -p "<prompt>" -e copilot -w .
miaco qmd-inquiry-decompose run --pde <uuid>   # enrich with knowledge base
miaco pde-to-st run --pde <uuid>               # generate Four Questions
```

Current `miaco decompose run` options include:

```bash
miaco decompose run \
  --prompt "<text>" \
  --engine copilot \
  --strategy standard \
  --workdir . \
  --format text
```

Important controls:

| Option | Use |
|--------|-----|
| `-p, --prompt <text>` / `-P, --prompt-file <path>` | Provide the source prompt. `@path` is also supported with `--prompt`. |
| `-e, --engine <engine>` | Engine: `copilot`, `claude`, `gemini`, `codex`, `pva`, or `hermes`. |
| `-m, --model <model>` | Override the selected engine model. |
| `--fallback-provider <provider>` | Root-only fallback after Copilot rate limits: `auto`, `none`, `codex`, `claude`, or a comma-separated chain. |
| `-s, --strategy <strategy>` | Decomposition strategy: `standard`, `iterative-refinement`, or `adversarial-consensus`. |
| `--add-dir <paths...>` | Add directories to the engine workspace and persist them in `meta.json`. |
| `--parent <uuid>` / `--parent-path <path>` | Attach a decomposition to an existing PDE lineage. |
| `--child-kind <kind>` | Relation to parent: `milestone`, `issue`, `sub-task`, `follow-up`, `refinement`, or `sibling`. |
| `--meta <json>` | Persist provenance under `meta.json`. |
| `--session-id <id>` | Persist a known engine session id for the PDE tree. |
| `--uuid <uuid>` | Supply a caller-owned UUID. |
| `--json` / `--format json` | Print the stored record for automation. |

### Strategy Selection

| Strategy | Use When | Current Guidance |
|----------|----------|------------------|
| `standard` | You need the stable baseline, compatibility with existing MCP flows, or a quick first-pass decomposition. | Default. Use for mcp-pde parity and low-risk decomposition. |
| `iterative-refinement` | The prompt is layered, lineage-heavy, ambiguous, or likely to benefit from multiple passes before action. | Recommended for Intent Analyst work and recursive PDE review. |
| `adversarial-consensus` | The decomposition needs explicit challenge, contrast, or competing readings. | Experimental. Use only when the local implementation is known to parse the strategy output cleanly. |

### Intent Analyst Use

An **Intent Analyst** is a PDE-facing role that reads a prompt as a structural-tension artifact before execution. It does not replace the implementer. It clarifies:

1. what the primary creative intent is;
2. which secondary intents are explicit or inferred;
3. where ambiguity should stay held rather than prematurely resolved;
4. whether `standard`, `iterative-refinement`, or `adversarial-consensus` best fits the prompt;
5. what child PDEs, issues, or refinement passes should be created.

For this role, start with:

```bash
miaco decompose run \
  --prompt-file prompt.md \
  --engine copilot \
  --strategy iterative-refinement \
  --workdir .
```

If the work is a child of an existing decomposition, add `--parent <uuid>` or `--parent-path <path>` with the appropriate `--child-kind`.

### Deep Lineage (miadi-code)

5-layer architecture in dedicated `pde/` module (11 files):

1. **Intent Extraction** — explicit + implicit intents with classification (CREATION, MODIFICATION, ANALYSIS, VALIDATION, INTEGRATION, COMMUNICATION)
2. **Dependency Analysis** — graph construction with parallelization detection
3. **Medicine Wheel Mapping** — direction assignment with ceremony type
4. **Workflow Generation** — staged execution templates (parallel/sequential/conditional)
5. **Execution Planning** — checkpoints, status tracking, fallback strategies

Dedicated MCP server (`mcp-pde-server.ts`) exposes 5 tools, 2 resources, 1 prompt. Webhook integration sends decompositions to the Miadi event hub.

### MCP Tools (mcp-pde / miadi-code)

| Tool | Purpose |
|------|---------|  
| `pde_decompose` | Build system prompt for LLM decomposition |
| `pde_parse_response` | Parse LLM response → DecompositionResult, store, optionally webhook |
| `pde_get` | Retrieve stored decomposition by ID |
| `pde_list` | List stored decompositions |
| `pde_export_markdown` | Export as git-diffable markdown |

**Current recommendation**: mcp-pde remains the stable MCP-standard decomposition path. Strategy-aware decomposition may be added to `jgwill/mcp-pde`, but until that support is present and verified, use `miaco decompose run --strategy ...` for `iterative-refinement` and `adversarial-consensus` work.

## Engine Configuration

The current miaco PDE surface supports several engines with different cost/quality profiles:

| Engine | Default Model | Binary | Use Case |
|--------|--------------|--------|----------|
| copilot | gpt-5-mini | `copilot` | Default — free tier, fast, good for most decompositions |
| claude | engine default / override | `claude` | Higher quality for complex prompts |
| gemini | engine default / override | `gemini` | Alternative semantic reading |
| codex | engine default / override | `codex` | Codex-aligned decomposition workflows |
| pva | provider/model override | PVA adapter | Provider-routed decomposition via `--pva-provider`, `--pva-model`, and `--pva-thinking` |
| hermes | provider passthrough | `hermes` | Hermes Agent workflows via `--hermes-provider` |

**Fallback**: use `--fallback-provider auto`, `none`, `codex`, `claude`, or a comma-separated chain for root-only fallback after Copilot rate limits.
**Cost guard (MIAC-18)**: Using opus or sonnet models with copilot engine is blocked to prevent unnecessary premium token consumption.
